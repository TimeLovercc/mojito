# Demo data

Everything here is about **Sam**, a made-up indie developer: shipping a side project (Loaflog, a sourdough bake
log app), learning guitar for an open mic, clearing out the closet for the new season. None of it is anyone's
real life, and it must stay that way: example data is only ever produced by `demo_data.py`, never exported from a
hub or database and edited.

| File | What it is |
|---|---|
| `demo_data.py` | The generator (Python 3.11+, standard library only; `build` also needs `openssl`). |
| `cors_proxy.py` | Lets the Expo dev web app (`npm run web`) talk to a local hub, which sends no CORS headers. |
| `../../docs/seed.example.json`, `../../mobile/mock/extra.json` | Generated by `demo_data.py mock`; read by the mock server. |

Dates are offsets from one day and times are wall-clock times, so the story is always "today": the mock server
shifts its data to today on start, and `seed` / `build` take `--day today`.

## 1. Look around with the mock server (no accounts, about 5 minutes)

```bash
cd mobile
npm install
cp .env.example .env              # EXPO_PUBLIC_MOJITO_TIMEZONE: your IANA zone (the app and the mock both read it)
MOCK_TOKEN=dev PORT=8788 MOCK_LANGUAGE=en npm run mock
npm run web                       # second terminal
```

In the app, set the hub address to `http://localhost:8788` and the token to `dev`. The mock keeps changes in
memory only; restart it to start over. Its own simulated replies (chat, notes) are in Chinese.

The committed files are in English. For Chinese, regenerate them (`--timezone UTC` keeps them neutral: the mock
re-reads every time as a wall-clock time in the zone of `mobile/.env`):

```bash
python3 examples/demo/demo_data.py mock --day today --timezone UTC --language zh --app-name Mojito \
  --morning-at 08:00 --evening-at 21:00 \
  --seed-out docs/seed.example.json --extra-out mobile/mock/extra.json
```

## 2. A real hub with Sam's history (the loop demo)

A throwaway hub instance on your machine: its own database, tokens and calendar file, nothing shared with a real
instance. `--timezone` becomes the hub's `MOJITO_TIMEZONE`; use the zone of `mobile/.env`.

```bash
OUT=~/mojito-demo
python3 examples/demo/demo_data.py build --day today --timezone America/Los_Angeles --language en --app-name Mojito \
  --morning-at 08:00 --evening-at 21:00 --port 8790 --public-url https://localhost:8790 \
  --fcm-credentials placeholder --out $OUT

# terminal 1: the hub
cd hub && set -a && . $OUT/hub.env && set +a && uv run uvicorn mojito_hub.main:app --host 127.0.0.1 --port 8790

# terminal 2: history through the API while the hub runs, then stop the hub (Ctrl-C) and backdate
python3 examples/demo/demo_data.py load --out $OUT
python3 examples/demo/demo_data.py backdate --out $OUT      # hub stopped; also saves $OUT/golden
# start the hub again (terminal 1)
```

Open the app against it: `python3 examples/demo/cors_proxy.py 8791 8790`, then `cd mobile && npm run web` and
set the hub address to `http://localhost:8791` with the token in `$OUT/clients/app-token.txt`.

- `$OUT/clients/maintainer.env` holds the hub address and token for the maintainer session (Claude Code, see
  `docs/maintainer.md`). Say something in the app, e.g. "rename the Today title to Morning", and watch it go from
  feedback to shipped.
- `ask --out $OUT` (hub running) adds one feedback that waits for your approval, to show the other path.
- `reset --out $OUT` (hub stopped) goes back to the backdated state before every take.
- `--fcm-credentials placeholder` writes a stand-in service account so the hub starts without a Firebase project;
  Android push is off, the web app does not need it. Pass a real service-account file to push to the Android app.
- `$OUT/web` is the hub's `MOJITO_WEB_DIR`: put a web build there to have the hub serve the app at `/app`.
- `worker.env` and `agent.env` connect a worker and a server agent to the same hub if you want them running too.
- `seed --out FILE` writes only the seed file, for starting a real hub with example content instead of an empty
  database.
